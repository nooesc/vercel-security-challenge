## SBX-013 proof hardening

The initial harness used one value for request correlation and credential injection, which could not prove retrieval of a value unknown to the guest. The harness now creates separate correlation and brokered canaries; only the correlation value enters the guest configuration.

Three fresh separated-secret harness runs reproduced the encoded dot-segment signal. An initial standalone PoC proved synthetic credential recovery through a controlled reflecting endpoint. Because that result depended on reflection, the final PoC replaced it with an authenticated outside action and added:

- a matched-path positive control;
- a canonical outside negative control;
- an explicit `/outside` action that returns `401` without the registered credential;
- an opaque operation ID rather than credential reflection;
- controller/observer SHA-256 comparison of the synthetic credential;
- a guard proving the brokered secret is absent from guest configuration.

Authenticated-action runs `639e6a5a-d7e3-45f7-ba90-2f2e28ede5ac` and `a1ef4cb0-eb8b-46ea-9178-8609953f7b50` passed both controls. In each run, canonical `/outside` returned `401`, while `/matched/%2e%2e/outside` routed to the same handler with the injected credential and authorized exactly one action. The guest response contained no credential. Both sandboxes stopped and deleted successfully. See the draft finding and redacted evidence under `findings/` and `pocs/SBX-013/`.

Final eligible-account reproductions used `swve@wearehackerone.com`, team `team_n98ERpVwV7HqmWRudAyK8sXQ`, and project `prj_CyyVykdN06Nrkla6KidZcecLgbCa`. Direct canonical `/outside` returned `401` without the brokered header or action, while the encoded case routed to that handler, received the synthetic credential, returned `200`, and authorized exactly one non-reflecting action. ## SBX-031: Encrypted ClientHello domain-allowlist bypass

Two fresh nonpersistent alias-account sandboxes reproduced an ECH-based network-policy bypass against one researcher-owned Cloudflare Worker. In each run, the controller first proved ordinary and ECH reachability under `allow-all`, then updated the active session to an exact user-defined policy whose only allowed domain was `cloudflare-ech.com`. Active-handle and independent-handle reads returned that exact policy for the original SDK session ID.

Under the restricted policy, an ordinary TLS connection exposing the Worker's hostname as SNI was blocked before any HTTP response. A fresh ECH connection to the same pinned IPv4 exposed only `cloudflare-ech.com` in the on-wire outer ClientHello, carried `encrypted_client_hello` extension `0xfe0d`, completed verified HTTP/2 for the denied inner Worker hostname, and returned the exact HMAC-derived operation ID for a fresh mode-`0600` synthetic operator-secret file. This proves that the provider accepted the encrypted inner identity and served that hostname; its internal decrypt-and-route steps are inferred rather than directly observed. The endpoint did not reflect the secret, and the raw secret did not enter guest source, configuration, arguments, output, or retained evidence.

The two private artifacts have SHA-256 values `db730f9f7fb8bd4e1c46422f89c8ac9ee889a9753e0b683a9a7db40e35c7c4c8` and `9cff3e172c53aa0c4730bdad07b73118665bb90aaf0cda619ad12302977d4dce`. No sandbox remained after either run. This meets the program's technical High-impact example of bypassing a domain allowlist to exfiltrate operator data, but report eligibility depends on whether Vercel intends a domain rule to constrain the effective ECH inner hostname or only the visible outer SNI. The public firewall documentation describes SNI-based enforcement but does not mention ECH or direct operators to an ECH-safe alternative.

A fully controlled provider-side strengthening experiment kept Cloudflare's ECHConfig byte-for-byte unchanged and varied only the outer SNI with OpenSSL `4.0.0`. The `cloudflare-ech.com` control completed verified ECH/TLS and returned `200 {"ok":true}` from the owned Worker. Changing only the outer SNI to the owned, Cloudflare-proxied `form-app.app` still emitted on-wire `encrypted_client_hello` (`0xfe0d`) but received fatal `handshake_failure(40)` before a certificate or application request. The alternate name published the identical ECHConfig and worked with plain SNI pinned to the same Worker IP. A separate serialized-config `public_name` rewrite was also rejected because the config is HPKE-bound. The arbitrary ordinary cover-name strengthening is therefore non-viable; the live finding retains the explicit prerequisite that `cloudflare-ech.com` is allowed.
