## SBX-013 proof hardening

The initial harness used one value for request correlation and credential injection, which could not prove retrieval of a value unknown to the guest. The harness now creates separate correlation and brokered canaries; only the correlation value enters the guest configuration.

Three fresh separated-secret harness runs reproduced the encoded dot-segment signal. An initial standalone PoC proved synthetic credential recovery through a controlled reflecting endpoint. Because that result depended on reflection, the final PoC replaced it with an authenticated outside action and added:

- a matched-path positive control;
- a canonical outside negative control;
- an explicit `/outside` action that returns `401` without the registered credential;
- an opaque operation ID rather than credential reflection;
- controller/observer SHA-256 comparison of the synthetic credential;
- a guard proving the brokered secret is absent from guest configuration.

Authenticated-action runs `639e6a5a-d7e3-45f7-ba90-2f2e28ede5ac` and `a1ef4cb0-eb8b-46ea-9178-8609953f7b50` passed both controls. In each run, canonical `/outside` returned `401`, while `/matched/%2e%2e/outside` routed to the same handler with the injected credential and authorized exactly one action. The guest response contained no credential. Both sandboxes stopped and deleted successfully. See the draft finding and redacted evidence under `findings/` and `pocs/SBX-013/`.

Final eligible-account reproductions used `swve@wearehackerone.com`, team `team_n98ERpVwV7HqmWRudAyK8sXQ`, and project `prj_CyyVykdN06Nrkla6KidZcecLgbCa`. Fresh runs `010c5a62-8f01-47dc-9ae3-dd3376c117fd` (`sbx_W1TMO10InoRL4LZAukEc8uty6Hqu`) and `4f79bbba-ef9b-42b0-b94a-40b13d4f86c0` (`sbx_qqvILzmYtGd9z5t9AF5qON4GX6e5`) reproduced the same authenticated-action differential with all controls and cleanup passing.

## Next-wave network tests

Two distinct controlled HTTPS tunnel hostnames were connected to the observer. Each live case used a new nonpersistent sandbox and all cleanup completed successfully.

| Test | Result | Interpretation |
| --- | --- | --- |
| `SBX-007` | Pass | Direct B was blocked and an A-to-B `302` produced no B request. |
| `SBX-011` | Pass | A-to-B redirect succeeded when both origins were allowed, but B did not receive A's controller-only brokered credential. |
| `SBX-008`, plain SNI mode | Signal reproduced twice; hold | A-only policy blocked direct B, while SNI A plus Host B executed a B-host action. This matches documented SNI-only enforcement and is not submission-ready. |
| `SBX-008`, credential-transform mode | Pass | Vercel's L7 proxy rejected SNI A plus Host B with `403 Forbidden: request authority does not match SNI`; no B event occurred. |
| `SBX-009`, HTTP/2 authority reuse | Pass | Fresh and reused B `:authority` streams were rejected with `403`; a final A stream on the same H2 session still succeeded, ruling out a dead-session false negative. |
| `SBX-010`, HTTP/1.1 connection reuse | Pass | After an accepted Host-A request on one verified TLS connection, a Host-B request on that same connection was independently rejected with `403`; no B event or action occurred. |
| `SBX-018`, live policy revocation | Hold; not reproducible on eligible account | One preliminary development-account run signaled stale state, but five conclusive hardened alias-account runs blocked all 15 retained sockets after acknowledged `deny-all`. |

The plain-mode result is being treated as a documented-design signal rather than a vulnerability. `SBX-010` run `503bebda-416d-4b02-af89-df64adf9e631` confirmed that the credential-transform proxy repeats its authority check on a reused HTTP/1.1 connection. `SBX-009` run `eb283770-84e0-45c3-9150-e56193841b5f` then confirmed equivalent per-stream enforcement on one verified H2 session with successful A streams before and after the rejected B stream. This closes the current authority-reuse family.

Initial `SBX-018` run `b7bbab25-b529-4e91-a1e6-8c7e7184a8a9` blocked both post-update paths. After hardening the fresh control to pin the exact pre-update edge IP, run `07e87373-ecca-4f71-8568-482f1c15fa44` produced a candidate: the update returned `deny-all` at `21:28:03.545Z`, the guest observed the later trigger at `21:28:03.834Z`, and the observer received the marked reused-socket request at `21:28:03.860Z` with the exact removed controller-only credential. Readiness, primary TLS, and post-update records share one socket ID and one handshake. A fresh TLS connection to the same `104.16.230.132:443` failed `EHOSTUNREACH`, the guest never received the credential, and the observer returned only `204`. Neighboring hardened runs blocked both paths, so this is being treated as a credible but intermittent stale per-flow policy/transform candidate pending a three-socket reproduction.

The hardened three-socket controller was then run from the required alias account. Five conclusive runs (`1cf012fa-…`, `a17e980e-…`, `3acb4f91-…`, `70616559-…`, and `84436f06-…`) passed every positive, timing, fresh-connection, socket-attribution, and cleanup control while blocking all 15 retained sockets. Run `01080874-…` was discarded as indeterminate because a timer fired one millisecond before its declared boundary; the scheduler now rechecks the wall clock and has a regression test. Because the candidate did not reproduce on the eligible account, `SBX-018` is not submission-ready and should remain on hold.

All cited nonpersistent sandboxes stopped and deleted successfully. Development-account artifacts are retained only as private research history; the final `SBX-013` evidence uses the required HackerOne-alias Vercel account.
